# The core six, and tzdata (CK-60). Pinned exactly, for a reason the four
# exception comments below each state in passing: the deployed artifact must
# be a function of the commit. Both services build with
# `pip install -r requirements.txt`, which re-resolves on every build, so an
# unpinned line means the running code can change with no commit behind it.
# It did. CK-58's deploy differed from CK-56's in TWO ways — the extraction
# in the diff, and SQLAlchemy 2.0.54 → 2.1.0, chosen by pip from a release
# whose wheels had reached PyPI hours earlier that same afternoon — and the
# check that compared the two deploys and called the extraction clean was
# comparing two changes while able to see one. A pinned requirement fails
# loudly at resolve time; an unpinned one fails silently in production.
# alembic is the sharpest case: render.yaml's preDeployCommand runs
# `alembic upgrade head` against the LIVE database while the old instance
# still serves, so an Alembic release arriving unreviewed executes DDL
# against production data inside the one window this project already has a
# whole discipline about. On policy: the four "deliberate exception"
# comments below are exceptions to ADDING a dependency at all (the
# transactional-email standard's plain-stdlib precedent), not to pinning —
# pinning rides inside each as its own clause ("a signing library moves on
# our decision, never pip's"). These six carried no reasoning either way;
# they were never considered. Pinning them extends that clause rather than
# overriding a decision, and the clause bears harder on the ORM every
# statement passes through than on a decoder. sqlalchemy[asyncio] is held at
# 2.0.54 DELIBERATELY, one minor BEHIND the last resolve: 2.0.54 is the
# version CK-51 through CK-56 were verified against — the verifier's 187 →
# 190 and every real destruction — while 2.1.0 has passed only a thin slice
# (190 schema assertions, /health, three rows read back), and the 437-test
# suite had, until CK-60 rebuilt the local environment from this file, only
# ever run against 2.0.52, a version neither deploy carried. Going back is
# returning to the known state; moving to 2.1 is its own reviewed change
# with its own checks, later. What this does NOT fix, in one sentence: the
# transitive tree still floats — greenlet, starlette, mako, pydantic-core
# and the rest re-resolve on every build — and the complete answer, a
# lockfile (`pip freeze` into a requirements.lock plus a changed
# buildCommand on BOTH services), is owed and is Steven's decision, not a
# step to slip into a pinning phase; its trigger is the first transitive
# package seen to move between two deploys with no commit behind it, or the
# prod cutover, whichever comes first. Still not license to add dependencies
# for problems that are actually simple.
fastapi==0.141.1
uvicorn[standard]==0.53.0
sqlalchemy[asyncio]==2.0.54
asyncpg==0.31.0
alembic==1.20.0
pydantic-settings==2.15.0
# IANA tz database for zoneinfo. Load-bearing on Windows dev machines (no
# system tzdb → available_timezones() would be empty and every profile
# timezone would 422); on Linux it is a consistent first-party source.
tzdata==2026.4
# py_webauthn (CK-10). A DELIBERATE exception to the transactional-email
# standard's "plain stdlib, no new dependency" precedent: that rule was about
# an HTTP POST, while WebAuthn is attestation parsing, COSE key handling, and
# signature verification — hand-rolling those would be the single worst
# decision available in the passkey phase. Do not read this pin as license to
# add dependencies for problems that are actually simple.
webauthn==3.0.0
# botocore (CK-33). The second deliberate exception, for the first one's
# reason: presigning an R2 upload is SigV4 — a canonical request, a scoped
# credential string, an HMAC chain — and a signature scheme hand-rolled
# "simply" is one that works today and fails on an edge case in production
# (a header the canonical form must sort, a key the encoding must escape).
# That is the WebAuthn mistake in a smaller coat. botocore ALONE, not boto3,
# chosen deliberately: boto3 is a convenience layer over this exact client
# (`boto3.client("s3")` IS a botocore client, and the presigner is
# botocore's), and what it adds — the resource API and s3transfer's managed
# multipart uploads — this arc does not use (video, the one multipart case,
# is out: pipeline record §6.4). One pin instead of two that must move
# together; three transitive packages instead of five. Pinned exactly, as
# webauthn is: a signing library moves on our decision, never pip's. Still
# not license to add dependencies for problems that are actually simple.
botocore==1.43.89
# Pillow + pillow-heif (CK-36). The third deliberate exception, and it is
# the first one's reasoning exactly: decoding JPEG/PNG/WebP/HEIC, applying
# an EXIF orientation, resampling with a real filter, and re-encoding to
# JPEG and WebP is codec work — hand-rolling any of it would be the WebAuthn
# mistake with pixels. pillow-heif is not optional: the intent allowlist
# admits image/heic because the launch shape is phone-first and HEIC is the
# iPhone default, and Pillow cannot open HEIC without it — with the decoder
# absent, the first photograph anyone uploads from a phone would pass the
# intent, land in quarantine, fail to decode and dead-letter (decision
# record 2026-09-09, §0). Its wheels bundle libheif, so Render's build is
# still `pip install -r requirements.txt` with no system package. Both pinned
# exactly, as webauthn and botocore are: a decoder moves on our decision,
# never pip's, and a new Pillow can change what an encoder writes. Still not
# license to add dependencies for problems that are actually simple.
Pillow==12.3.0
pillow-heif==1.7.0
